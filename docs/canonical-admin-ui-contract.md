MiseLedger Canonical Admin UI Contract

Status: Baseline specification
Source of truth: MiseLedger main at 80918ca7d31799fe1baea36b06c2ec7f7c11c698
Scope: Authenticated application UI only
Change class: Visual consistency specification only

1. Governing Principle

This contract formalizes patterns that are already repeatedly established in MiseLedger. It does not redesign the application, change behavior, introduce new domain semantics, add dependencies, or require immediate migration of existing pages.

The existing Tailwind CSS 4 semantic token system and shadcn new-york configuration are the visual foundation. Components must prefer background, foreground, card, muted, primary, destructive, border, input, ring, and existing sidebar tokens rather than introducing parallel color or radius systems.

Area	Canonical contract	Intentional exception or tolerated existing variance
Page shell	Normal domain index/report pages use the existing global AppLayout and sidebar shell. Page content should normally use flex flex-1 flex-col gap-6 p-4 sm:p-6. Breadcrumb metadata remains page-owned through the repository's existing page layout convention.	Dashboard has a denser gap-4 composition. Settings receives [AppLayout, SettingsLayout]. Existing pages using md:p-6 or workflow-specific p-4 are not migrated by this spec.
Page header	Primary domain pages use one h1 with text-2xl font-semibold tracking-tight, optional mt-1 text-sm text-muted-foreground supporting copy, and a responsive flex flex-wrap gap-2 action area. Primary creation action uses the default Button; secondary navigation/actions use outline or another existing semantic variant.	Dashboard's active-organization banner is contextual application chrome. Settings uses its nested Heading hierarchy and an sr-only page h1. Transactional forms may use a simpler workflow heading.
Surfaces	Standard administrative surfaces use rounded-xl, semantic border, bg-card, and consistent p-4 or p-5. Complex table/filter containers may use overflow-hidden. Panel headers use a bottom border, px-4, text-sm font-semibold, and optional text-xs text-muted-foreground description.	shadow-sm is currently mixed across legitimate pages, so elevation remains optional rather than a required token. Workflow sections may intentionally omit bg-card or shadow while retaining border/radius hierarchy.
Typography	Instrument Sans and the semantic Tailwind typography already configured remain authoritative. Page title is 2xl/semibold; section title is normally sm/semibold or contextual font-semibold; body/help copy uses text-sm; tertiary metadata uses text-xs text-muted-foreground. Numeric operational data should use tabular-nums, with right alignment in numeric table columns.	SKU/code values may use monospace where they function as identifiers. Dashboard KPI values use the existing larger metric treatment. Settings uses the Heading small variant.
Forms	Use Inertia <Form> following existing repository behavior. Standard field composition is grid gap-2 with Label, the existing shadcn control, and InputError. Default controls align to the existing h-9, rounded-md, semantic border/background, focus ring, disabled state, and aria-invalid treatment.	Native <select> remains valid for simple server-submitted forms because it is already widespread and preserves native form semantics. It must visually match Input. Do not migrate native selects wholesale to Radix Select in this spec.
Form actions	Submit/save is the strongest available action. Cancel, Back, Clear, and secondary navigation use outline, ghost, or the repository-established equivalent. Action groups wrap with gap-2 instead of relying on fixed desktop width. Processing states disable the triggering action and retain existing Inertia behavior.	Lifecycle actions such as Approve, Finalize, Ship, Receive, and Cancel remain controlled by their domain workflow and authorization rules.
Filters	Filterable index/report pages use a GET <Form>, responsive grid, repository-backed query state, and a bounded surface. Search uses the existing Input, optionally with a Lucide search icon. Apply is primary; Clear/Reset is secondary. Fields use visible labels where space permits, or sr-only labels in intentionally compact toolbars.	Number and arrangement of filters remain domain-specific. This contract does not introduce filters to pages that do not need them or change backend filtering behavior.
Tables	Continue using semantic HTML tables. Place wide tables in overflow-x-auto and give them an intentional minimum width instead of compressing critical data. Use w-full text-sm, px-4 py-3 cells, muted medium-weight headers, borders between rows, and subtle hover:bg-muted/30 where rows contain interaction. Numeric columns are right-aligned and tabular-nums.	There is no shared ui/table.tsx at current HEAD, so this spec does not create one or require a table abstraction. Domain workflow review tables may use lighter spacing where they are subordinate to a form.
Table accessibility	Use scope="col", an sr-only caption where surrounding content does not sufficiently identify the data, aria-sort for sortable columns, visible focus treatment on interactive cell links, and an accessible action header. Icon-only actions require aria-label; decorative icons use aria-hidden="true".	None. These are application-wide accessibility requirements.
Statuses	Badge is the canonical compact status primitive. Every state must include readable text. Workflow status mapping stays explicit and domain-owned. When colors distinguish multiple lifecycle states, use an icon or other non-color cue as already demonstrated by Purchase Orders, and provide matching dark-mode treatment.	Do not create a single global business-status color map. Active, Draft, Approved, Partially received, Received, Cancelled, count states, transfer states, and other enums retain their own domain meaning.
Dialogs	Use the existing Radix/shadcn Dialog primitives. Dialogs should have a clear DialogTitle, supporting DialogDescription when clarification is needed, responsive DialogContent, and appropriately ordered primary/destructive and secondary actions. Long forms may add viewport-bounded height and internal scrolling.	Dirty-state protection, confirmation requirements, and lifecycle dialogs remain workflow-owned. Existing useGuardedDialog, navigation guards, and confirmation behavior must not be removed or weakened for visual consistency.
Empty states	Empty content stays inside the owning surface. Use a concise font-medium title plus text-sm text-muted-foreground explanation. Filtered-empty copy should tell the user to adjust or clear filters. First-use copy may identify the valid next action, but only when the user is authorized to perform it. A muted icon container is optional.	Dashboard's dense operational panels may use compact text-only empty states instead of full illustrations or calls to action.
Pagination	Existing server pagination is the canonical pattern: top border, px-4 py-3, range summary, Previous and Next small outline buttons, Page X of Y, disabled boundary buttons, and responsive column-to-row composition. Inertia pagination links preserve scroll and state where currently required. Hide navigation controls when there is only one page.	No numbered pagination package, infinite-scroll dependency, or replacement pagination system is introduced by this contract.
Responsiveness	Build mobile-first. General page padding starts at p-4, increasing to p-6 on roomier viewports. Headers and action groups stack or wrap before becoming horizontal. Filter grids collapse naturally. Wide data tables scroll horizontally rather than hiding business-critical columns. Dialogs remain viewport-bounded.	Settings intentionally changes to a sidebar/content layout at lg. Dashboard intentionally introduces multi-column metric and side-panel layouts at larger breakpoints.
Dark mode	The existing .dark semantic variables in app.css are authoritative. Use semantic background, foreground, border, muted, input, ring, destructive, card, and sidebar tokens. Any custom operational status accent must include an equivalent dark variant.	Existing primitive-owned values such as the dialog overlay and destructive button treatment remain implementation details of those shared primitives.
Accessibility	Preserve keyboard operation, visible focus-visible rings, semantic headings, explicit form labels, aria-invalid, readable validation messages, semantic tables, accessible dialogs, labeled icon actions, and text/non-color status meaning. Never remove information or permissions from assistive-technology users merely to simplify visual layout.	Settings may use an sr-only page-level h1 because its visible hierarchy is supplied by the nested Settings layout.
Icons	Continue using the already configured Lucide icon set. Decorative icons are hidden from assistive technology. Icons supplement labels and status meaning rather than replacing text unless the control has a clear aria-label.	Metric cards and compact action buttons may be icon-forward where their existing accessible labels remain intact.
Design tokens	Existing CSS variables, Tailwind spacing/radius utilities, shadcn variants, and shared components are the contract. Do not introduce page-local replacements for colors, button systems, focus treatments, typography scales, or radius systems when an established token already exists.	Domain-specific semantic accent classes are acceptable when they communicate real operational state and include dark-mode equivalents.
2. Canonical Evidence Pages

The strongest general-purpose patterns come from Inventory Items, Stock on Hand, and Purchase Orders. They consistently demonstrate the page header, responsive content spacing, filters, bounded surfaces, semantic tables, empty states, status presentation, and server pagination patterns.

The shared Button, Input, Label, Badge, Dialog, and available Select primitives remain the canonical low-level controls rather than page-specific recreations.

3. Intentional Exceptions

Dashboard: It is an operational overview, not the canonical CRUD/index template. Its active-organization banner, gap-4 density, metric grid, multi-panel composition, and compact activity/task treatments are valid dashboard-specific patterns. DashboardMetricCard may still be reused outside Dashboard when a page already has a meaningful operational summary, but metrics must not be invented merely to fill the layout.

Settings: Settings intentionally receives the nested SettingsLayout, constrained content width, internal settings navigation, mobile separator, and smaller section-heading hierarchy. It must not become the template for inventory, purchasing, reporting, or other administrative domain pages.

Domain workflows: Purchase ordering, receiving, counts, transfers, waste, adjustments, and similar transactional screens may require sequential sections, line-item editors, dirty-state guards, read-only lifecycle views, confirmation dialogs, and permission-gated state transitions. The canonical controls, tokens, typography, responsive behavior, dark mode, and accessibility rules apply, but the workflow structure and business behavior remain domain-owned.

4. Explicit Non-Goals
No routes, controllers, actions, policies, authorization, validation, Inertia contracts, database queries, schemas, or business rules change.
No stock-ledger, procurement, receiving, count, transfer, waste, recipe, or organization behavior changes.
No new npm or Composer dependency.
No new design-system framework.
No global status semantics beyond existing domain enums.
No broad page-by-page migration.
No forced conversion of native selects to Radix Select.
No new table or pagination abstraction merely for architectural symmetry.
No visual metric, filter, action, or data field invented without existing product value and repository-backed data.
No direct repository modification as part of this specification.
5. Adoption Rule

For future UI work, apply this contract only to the page or component already in scope. Reuse an existing shared primitive first, preserve all current behavior and authorization, and only extract a reusable component after the same pattern is genuinely repeated and the extraction reduces duplication without changing semantics.

A page is compliant when it looks and behaves like part of the same MiseLedger application in light and dark mode, remains keyboard and screen-reader operable, preserves existing responsive behavior and domain semantics, and introduces no parallel styling system or unnecessary dependency.
